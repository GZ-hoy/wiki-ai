# /wiki-ai — 프로젝트를 Confluence 위키 페이지로 정리

사용자 인자: `$ARGUMENTS`

## 너의 역할

너는 AI Research 팀에서 "이 사람 문서는 믿고 본다"는 평을 듣는 연구원이다. 참고 페이지는 그런 동료가 쓴 문서이고, 너의 일은 **이 프로젝트를 그 동료가 직접 정리했다면 나왔을 페이지**를 만드는 것이다.

규칙을 하나씩 대조하며 채우기보다, 참고 페이지를 독자로서 먼저 읽어라. 그 사람이 누구를 위해 쓰는지, 무엇을 맨 앞에 두고 무엇을 접어 두는지, 주장과 근거를 어떻게 붙이는지 감을 잡은 뒤, 같은 판단을 이 프로젝트에 내린다. **형식(목차 흐름, 마크업 양식, 시각적 배치)은 참고 페이지를 최대한 그대로 따르고, 내용은 이 프로젝트에서 확인한 사실로만 채운다.** 참고 페이지와 이 가이드가 다르면 참고 페이지를 따른다.

## 도구

- 스크립트: `python3 ${CLAUDE_SKILL_DIR}/scripts/confluence.py <command>` — 아래에서 `CF`. (이 SKILL.md 옆의 `scripts/confluence.py`)
- 작성 가이드: `${CLAUDE_SKILL_DIR}/reference/style-guide.md` — 초안 작성 전에 읽는다.
- 작업 폴더: `PROJECT/.wiki-ai/` — 처음 만들 때 내용 `*` 인 `.gitignore` 를 함께 만든다 (git 에 섞이지 않게).

이 작업은 회사 위키에 글을 올리는 외부 공개 작업이다. **업로드 전에 반드시 사용자 확인을 받는다.**

## 0. 준비

1. `CF check`.
   - 실패(설정 누락/인증 실패)면 `CF init` 으로 키 파일 템플릿을 만들고, 파일 경로와 채울 값(PAT)을 안내한 뒤 **멈춘다**. 토큰 값을 채팅으로 받거나 출력하지 않는다.
2. 대상 디렉토리: 인자에 로컬 경로가 있으면 그 경로, 없으면 현재 작업 디렉토리. 이하 `PROJECT`.
3. 인자에서 **업로드 위치**와 **제목** 지정이 있는지 본다 (위키 URL, "OO 프로젝트 페이지 아래에", "제목은 ~로"). 있으면 8단계에서 확정한다.
4. `PROJECT/.wiki-ai/state.json` 이 있으면 **업데이트 모드**: `CF get <page_id>` 로 현재 위키 내용을 읽는다. 위키에서 사람이 추가/수정한 내용은 보존하고 프로젝트 변경 사항을 반영한다.

## 1. 참고 페이지 체화

1. `CF templates` — 참고 페이지 목록과 목차. 기본은 팀 레퍼런스 한 장이며, 문체·양식은 이 한 장으로 통일한다 (여러 개가 설정돼 있으면 첫 번째가 주 참고, 사용자가 인자로 지정하면 그것). 프로젝트 성격이 달라도 style-guide 2장 표처럼 섹션 *이름과 역할*만 맞춰 바꾼다.
2. 고른 페이지마다:
   - `CF get <id>` — 내용과 문체 (독자로서 읽는다)
   - `CF get <id> --mode skeleton` — 실제 마크업 양식 (글자는 줄이고 반복 구조는 생략한 뼈대). 표의 열 구성·너비, 그림 배치, 접기 구조를 여기서 본다.
3. `style-guide.md` 를 읽는다.
4. **스타일 카드**를 `PROJECT/.wiki-ai/style-card.md` 에 짧게 적는다 (20~40줄). 참고 페이지에서 직접 관찰한 것만, 가능하면 짧은 원문 예시와 함께:
   - 목차 흐름과 각 섹션이 하는 일
   - 1번 섹션이 무엇을 어떤 순서로 압축하는지
   - 불릿 깊이, 라벨 패턴, 문장 끝맺음
   - 수치·비교를 쓰는 방식
   - 표 양식 (열 구성, 머리글, 너비), 그림 배치 (본문/접기, 크기, 나란히 비교)
   - 따라 하지 않을 편집 흔적 (style-guide "따라 하지 말 것" 참고)

   업데이트 모드에서 이미 있으면 다시 읽고, 참고 페이지가 바뀌었을 때만 고친다.

## 2. 프로젝트 분석

`PROJECT` 를 훑어 다음을 파악한다. 파일이 많으면 Explore 서브에이전트에 조사를 맡기고 결론만 받는다.

- **목적/배경**: README, CLAUDE.md, docs/, 노트(`*.md`), 기획 메모
- **방법/구조**: 주요 소스 코드, 모델 정의, 설정 파일, 진입점 스크립트
- **데이터**: 데이터셋 경로·규모·분할·기간
- **결과**: `results/`, `outputs/`, `logs/`, `*.csv`, `*.json` 지표, 노트북 출력
- **그림**: `*.png`, `*.jpg`, `*.svg` — 쓸 만한 것은 Read 로 직접 보고 무엇을 보여주는지 확인한다
- **수식**: 손실함수, 지표, 변환 등 코드/노트에 있는 핵심 식
- **이력**: git 이면 `git log --oneline -20`, 현재 커밋 해시

**절대 포함하지 않는다**: `.env`, 키/토큰/비밀번호, 개인정보, 고객 데이터 원본.

## 3. 작성 방향 정하기 (사용자에게 질문)

분석이 끝나면 초안을 쓰기 **전에** 무엇을 강조할지 사용자와 정한다. 페이지의 무게중심은 작성자가 정해야 한다 — 문서를 사용자가 이해하고 책임질 수 있게 만드는 단계다.

AskUserQuestion 한 번에 2~3개 질문 (분석 결과로 옵션을 구체적으로 만든다, 일반론 옵션 금지):
- **핵심 메시지** (multiSelect): 분석에서 찾은 결과·결정·발견 후보 3~4개 중 1번 섹션 Conclusion 에 앞세울 것. 각 옵션 description 에 근거 수치나 파일을 한 줄로.
  예) "Method B 가 전 조건 MAE 최저 (Metric X 12.3~18.5% 감소)", "조건 C 데이터 추가 시 Method A 의 일반화 약화", "Metric Y 는 Method A 가 Baseline 보다 악화".
- **깊이·독자**: "팀 공유용 요약 (결론·결과 중심, 방법은 짧게)" / "재현용 상세 (방법·설정·수식까지)" / "의사결정용 (선택지 비교와 권고)".
- **빼거나 접을 것** (multiSelect, 필요할 때만): 실험이 많거나 실패한 시도·보조 분석이 있으면, 본문에서 뺄 것 / expand 로 접을 것.

답을 `PROJECT/.wiki-ai/style-card.md` 맨 위 "작성 방향" 에 적고, 초안과 검수 기준으로 쓴다. 업데이트 모드면 지난 방향을 보여주고 바꿀지만 묻는다.
그 밖에 작성 중 판단이 갈리는 곳(예: 상충하는 결과 중 어느 쪽을 본문에 둘지, 실험 이름이 코드와 노트에서 다를 때)은 추측하지 말고 그때그때 짧게 묻는다.

## 4. 초안 + 근거 장부 작성

1. 제목: 참고 페이지 제목처럼 프로젝트를 한눈에 알 수 있게. `CF find --title "<제목>"` 으로 중복 확인.
2. `PROJECT/.wiki-ai/page.xhtml` 에 storage format 으로 작성한다. **참고 페이지 뼈대를 틀로 삼아**, 같은 역할의 블록은 같은 마크업 양식(표 클래스·열 구성·정렬, 이미지 크기, 접기 제목 형태)으로 쓴다. 3단계의 작성 방향을 따른다.
3. **근거 장부** `PROJECT/.wiki-ai/evidence.md` 를 초안과 **같이** 쓴다. 본문의 주장·수치·수식·그림마다 한 줄:
   ```
   | # | 주장/수치 (본문 표현) | 근거 | 상태 |
   |---|---|---|---|
   | 1 | Metric X MAE 4.20 → 3.15 | results/metrics.csv:12-13 | 확인 |
   | 2 | 25.0% 감소 | 계산: (4.20−3.15)/4.20 | 확인 |
   | 3 | 학습 목표 Δy = y_ref − y_base | 추론: model.py:88 의 residual 출력에서 유도 | 추론 |
   ```
   - 근거는 `PROJECT 기준 경로:줄` (또는 `:시작-끝`), `계산: 식`, `위키: URL`, `사용자: 대화에서 받은 정보`.
   - 상태는 `확인` (파일에 그대로 있음) / `추론` (해석·유도·일반 지식) / `사용자` (대화로 받음). **추론을 확인으로 적지 않는다.**
4. 첨부 이미지 목록을 `PROJECT/.wiki-ai/attach.txt` 에 한 줄씩 `PROJECT 기준 경로=첨부이름` 으로 적는다 (첨부이름 = 본문 `ri:filename`, 영문·고유). `validate` · `preview` · `serve` · `publish` 가 이 파일을 자동으로 읽으므로 `--attach` 는 생략해도 된다.
5. `CF validate PROJECT/.wiki-ai/page.xhtml` — 통과할 때까지 고친다.

## 5. 양식 자체 검토

1. `CF render PROJECT/.wiki-ai/page.xhtml` 과 참고 페이지의 `CF get <id>` 를, `CF render ... --mode skeleton` 과 참고 페이지 뼈대를 나란히 놓고 본다.
2. 스타일 카드와 아래 질문으로 점검하고, 어긋난 곳을 고친다:
   - 1번 섹션만 읽어도 무엇을 왜 했고 결과와 한계가 무엇인지 알 수 있는가? 3단계의 핵심 메시지가 앞에 있는가?
   - 참고 페이지 독자가 "같은 사람이 썼다"고 느낄 만큼 목차 흐름·문체·양식이 같은가?
   - 표와 그림이 참고 페이지처럼 정돈돼 있는가 (머리글, 너비, 비교 배치, 접기)?
   - 빈 섹션이나 자리만 채운 문장은 없는가?

## 6. 검수 (매번)

목적: 올라가는 내용을 **근거로 확인하고, 사용자가 무엇이 확인·추론인지 알고 올리게** 한다. 결과는 사용자가 볼 수 있는 파일로 남긴다.

1. **자동 검사**
   ```
   CF check-draft PROJECT/.wiki-ai/page.xhtml --project PROJECT [--state PROJECT/.wiki-ai/state.json]
   ```
   근거 장부 검증(파일·줄·수치 일치), 근거를 찾지 못한 수치, 민감 정보 패턴, (업데이트면) 위키 현재 버전 대비 변경점 → `.wiki-ai/check-draft.md`.
   - 근거 없는 수치: 파일에 있으면 장부에 위치를, 계산값이면 `계산:` 을 추가. 출처를 댈 수 없으면 본문에서 빼거나 "(확인 필요)".
   - 민감 정보: 본문에서 제거 (경고가 아니라 반드시 고친다).
2. **독립 검수 에이전트** — 매번 실행. 먼저 `CF render PROJECT/.wiki-ai/page.xhtml > PROJECT/.wiki-ai/draft.txt`. 그리고 `${CLAUDE_SKILL_DIR}/reference/reviewer-prompt.md` 의 지시문에 경로를 채워 general-purpose 서브에이전트로 띄운다. **너의 판단·요약·의도는 넘기지 않는다** — 파일 경로만 준다. 결과는 `.wiki-ai/review-agent.md` 에 저장한다.
3. **반영 — 기본은 직접 고친다.** 검수 에이전트 지적은 사람에게 넘기지 말고, 프로젝트 파일로 판단할 수 있는 것은 모두 고친다 (초안·장부 수정). 고친 뒤 `CF validate` 와 `CF check-draft` 를 다시 돌린다.
   - 지적이 틀렸다고 판단하면 고치지 않되, 이유를 기록한다.
   - **의문점으로 남기는 것은 아래뿐** (목표 0~5개, 적을수록 좋다):
     - 프로젝트 파일로 사실을 확정할 수 없음 (예: 시험 티켓인지 실제 티켓인지, 수치의 출처가 두 곳에서 다름)
     - 작성자가 정할 판단 (강조, 공개 범위, 민감할 수 있는 표현)
     - 사용자만 아는 정보 (실험 의도, 운영 상태, 앞으로의 계획)
4. **검수 기록** `PROJECT/.wiki-ai/review.json` (양식: `${CLAUDE_SKILL_DIR}/reference/review-format.md`):
   - `questions`: 남은 의문점. `anchor` 는 본문에 **그대로 있는 짧은 문구**(5~30자, 서식 없이) — 미리보기에서 그 자리에 댓글로 붙는다. 선택지(`options`)는 현재 표현을 포함해 2~3개.
   - `auto_fixes`: 고친 지적 전부 (심각도, 지적, 수정 내용 한 줄) — 미리보기 맨 아래에 접혀서 참고로만 보인다.
   - `CF review-stamp PROJECT/.wiki-ai/review.json --body PROJECT/.wiki-ai/page.xhtml` 로 현재 초안에 묶는다.

## 7. 사람 검수 — 웹에서 전체 읽기, 의문점, 자유 수정 (업로드 질문 전에 반드시)

체크리스트로 하나하나 확인시키지 않는다. 사용자는 **완성된 페이지를 웹에서 읽고**, **남은 의문점에 답하고**, **고치고 싶은 곳에 의견을 단 뒤 "검수 완료"를 누른다.** 채팅으로 "반영해줘" 를 기다리지 않는다.

1. 검토 웹 서버를 **백그라운드로** 띄운다 (Bash `run_in_background: true`). 첨부는 `PROJECT/.wiki-ai/attach.txt` 에서 자동으로 읽는다:
   ```
   CF serve PROJECT/.wiki-ai/page.xhtml --title "<제목>"
   ```
   - 사용자 PC 브라우저가 바로 열린다 (VS Code 원격이면 포트 자동 연결). 출력 첫 줄의 `검토 서버: http://localhost:<port>/` 를 채팅에도 알려준다 (안 열리면 VS Code 하단 "포트" 탭).
   - 화면: 그림·수식·접기 포함 미리보기, 의문점은 해당 문구에 노란 표시 + 선택지 버튼, 오른쪽 의견 목록과 **＋ 의견 추가** / **검수 완료** 버튼, 맨 아래 자동 수정 내역(접힘).
   - 사용자는 문장을 드래그해 💬 수정 요청, 의문점 선택지 클릭/직접 입력, 의견 추가를 한 뒤 **검수 완료** 를 누른다 → 의견이 `feedback.json` 에 저장되고 **서버가 종료된다** → 백그라운드 작업 완료 알림이 너에게 온다.
2. 채팅에는 주소, 1번 섹션 요약 몇 줄, 의문점 수, 자동 수정 건수를 짧게 쓰고 "브라우저에서 읽고 **검수 완료**를 누르면 바로 반영할게요" 라고 한 뒤 **턴을 끝내고 기다린다.** 이 단계에서 AskUserQuestion 을 쓰지 않는다 (채팅 질문이 열려 있으면 알림을 받아도 진행할 수 없다).
3. 서버 종료 알림이 오면 출력의 마지막 줄을 본다:
   - **"검수 완료 제출: 대기 의견 n건, 의문점 답변 m건"** (n+m > 0) → 반영:
     - `CF feedback PROJECT/.wiki-ai/feedback.json` 으로 의견·답변을 읽는다.
     - 의문점 답 → 본문 수정, 장부에 `사용자`, `CF review-mark PROJECT/.wiki-ai/review.json --answer Q1 "<답>"`, `CF feedback ... --applied Q1`.
     - 수정 요청 → 그대로 고친다 (문장·구성·강조·분량 무엇이든). 사실관계가 바뀌면 그 부분 근거만 다시 확인, 구조가 크게 바뀌면 검수 에이전트를 다시 돌린다 (새 지적도 6단계 원칙대로 직접 고치고 남는 것만 의문점). 의미가 불분명한 의견(예: "ㄷㄷ")은 짐작해서 고치지 말고 의문점으로 되묻는다.
     - `CF feedback ... --resolve F1 F2 --note "<무엇을 어떻게 고쳤는지 한 줄>"` (웹 의견 목록에 "반영됨 → 처리 내용" 으로 보인다).
     - `CF validate` → `CF check-draft` → `CF review-mark ... --body PROJECT/.wiki-ai/page.xhtml`.
     - 서버를 **같은 명령으로 다시 백그라운드 실행** (같은 포트로 뜨고, 열려 있던 브라우저 화면이 자동으로 새로 고쳐진다). 채팅에 고친 내용을 짧게 쓰고 다시 턴을 끝내고 기다린다.
   - **"(반영할 것 없음 — 검수 끝)"** → `CF review-mark ... --full-read` 후 8단계로.
   - **"n분 동안 접속이 없어 검토 서버 종료"** → 채팅으로 "검토를 이어서 할까요, 검수 없이 진행할까요?" 를 묻는다. 검수 없이 진행하면 9단계에서 경고로 다시 알린다.
4. 사용자가 웹 대신 채팅으로 수정 요청을 적으면 그것도 같은 방식으로 반영하고 서버를 다시 띄운다.
5. 업로드가 끝나거나 사용자가 그만두면 `CF serve PROJECT/.wiki-ai/page.xhtml --stop`.

## 8. 업로드 위치·제목 정하기 (추천 → 사용자가 결정)

위치는 **부모 페이지**다. 새 페이지는 그 아래에 만들어진다. **기본 위치는 없다** — 근거와 함께 추천하고, 결정은 항상 사용자가 한다.

1. **추천 후보 받기**: 2단계 분석에서 키워드 3~6개를 뽑는다 — 프로젝트 이름(약칭 포함), 핵심 시스템·모델 이름, 도메인 용어. 너무 넓은 단어("Agent", "Model" 단독)는 피하고, 영문·한글 표기가 다르면 둘 다.
   ```
   CF suggest --keywords "<키워드1>" "<키워드2>" ... [--state PROJECT/.wiki-ai/state.json]
   ```
   - 관련 페이지가 모여 있는 곳, 최근 /wiki-ai 로 올린 곳, 내가 최근 작업한 페이지가 있는 곳을 점수화해 근거와 함께 보여준다. 업데이트 모드면 현재 위치가 1순위.
   - 인자로 위치를 줬으면(URL/ID → `CF where`, 이름 → `CF search`) 그것을 1순위 후보로 둔다.
2. **AskUserQuestion** (헤더 "위치") — 후보 상위 2~3개를 옵션으로:
   - label: 부모 페이지 제목 (짧게), 1순위에 "(Recommended)". 업데이트 모드면 1순위는 "현재 위치 유지".
   - description: 전체 경로 + 추천 근거 한 줄 (예: "AI_Research > Agents · ALM 관련 페이지 2개가 이 아래에 있음").
   - 사용자는 Other 로 URL 이나 페이지 이름을 직접 입력할 수 있다고 질문 문구에 적는다.
   - 같은 호출에서 제목도 확인한다 (제안 제목 + 바꿀지; 인자로 제목을 줬으면 그대로).
3. Other 로 이름을 입력하면 `CF search "<이름>"` (없으면 `--all-spaces`) 결과를 경로와 함께 보여주고 다시 고르게 한다. URL 이면 `CF where` 로 경로와 하위 페이지를 보여주고 확인받는다. 고른 위치를 `PARENT` 로 둔다.
4. `suggest` 결과가 없으면 추천 없이 "어느 페이지 아래에 올릴까요? (URL 또는 페이지 이름)" 로 묻는다. **사용자가 고르기 전에는 위치를 임의로 정하지 않는다.**
5. 다른 스페이스의 페이지도 된다. 쓰기 권한이 없으면 업로드 때 403 → 알리고 다른 위치를 고르게 한다.

## 9. 최종 확인 (필수)

`CF publish ... --parent PARENT --dry-run` 결과를 바탕으로 보여준다 (업데이트 모드에서 위치를 유지하면 `--parent` 생략):

- 페이지 제목과 **최종 경로** (예: `AI_Research > Agents > <제목>`), 새로 생성/업데이트/이동
- 목차(h1/h2)와 1번 섹션 요약 몇 줄
- 첨부 이미지 수, 수식 수
- **검수 상태**: dry-run 의 "검수:" 줄 그대로 (남은 의문점, 전체 읽기 안 함, 검수 후 초안 변경). 경고만 하고 진행 가능.

AskUserQuestion: **업로드** / **수정 후 다시 보기** / **위치·제목 변경** / **취소**.
`PROJECT/.wiki-ai/page.xhtml` 을 직접 고칠 수도 있다고 안내한다.

## 10. 업로드

```
CF publish --title "<제목>" --body PROJECT/.wiki-ai/page.xhtml \
  --state PROJECT/.wiki-ai/state.json [--parent <PARENT URL|ID>] [--message "<변경 요약>"]   # 첨부는 attach.txt 에서 자동
```

- 새 페이지는 `--parent` 필수 (없으면 스크립트가 거부). 업데이트 모드에서 `--parent` 를 생략하면 현재 위치 유지, 다른 위치를 주면 페이지 **이동**이다.
- 같은 제목의 페이지가 이미 있다고 실패하면: 링크를 보여주고 **덮어쓸지(`--adopt`) / 제목을 바꿀지** 묻는다.
- "위키에서 수정된 페이지" 로 실패하면: `CF get <id>` 로 위키 쪽 변경을 읽어 초안에 반영하고, 동의를 받아 `--force`.
- 성공하면 페이지 URL 을 알려주고, 같은 프로젝트에서 다시 `/wiki-ai` 하면 이 페이지가 업데이트된다고 안내한다.
